Perfetto's trace_processor fuzz target parses an input trace through a chain of format-specific handlers; when the trace bytes look gzip/ctrace-compressed, control passes to the compressed-trace handler before the payload is handed to zlib. That handler assumes every first chunk it ever sees begins with a fixed 7-byte literal marker used by one particular legacy container format, and on the very first call it unconditionally advances the input pointer past that marker and shrinks the byte count by the same fixed amount — with no check that the chunk is actually at least that long, and no check that the marker is even present. When the fuzz harness hands it a chunk shorter than the marker itself, subtracting the marker's length from the (unsigned) remaining-byte count wraps around to a huge value instead of going negative, while the pointer has simultaneously been walked one byte past the end of the small heap buffer that was allocated for the actual input. That corrupted (pointer, huge-length) pair is passed straight into zlib's stream-decompression call as "here is the compressed data, keep consuming until you've read this many bytes." The very first byte the decompressor tries to load is that one-past-the-end pointer, so the out-of-bounds read happens on entry, deep inside third-party zlib code, even though the invalid pointer/length were both computed entirely in Perfetto's own wrapper before zlib was ever called. AddressSanitizer flags a 1-byte heap-buffer-overflow read immediately adjacent to a 6-byte heap allocation (the undersized fuzzer input buffer itself).
