A bug in Capstone's 6502/MOS 65xx disassembler (MemorySanitizer build): decoding certain instructions leaves part of the per-instruction "groups" list uninitialized, and a later query over that list reads the stale slot as if it were a valid group id. Root cause: the routine that populates instruction details always writes a newly discovered group into the first slot of the fixed-size groups array and then bumps the group counter, instead of writing into the slot indicated by the counter itself; when an instruction triggers two separate group classifications in the same decode, the second write clobbers the first slot rather than filling the next one, so the counter ends up claiming two valid entries while only the first array slot was ever actually written. The second, never-initialized slot still holds whatever garbage was on the heap when the instruction-detail structure was allocated, and once the fuzz target iterates the reported groups and looks each one up by name, that lookup reads the uninitialized slot's value straight out of heap memory.
