radare2's binary-info/analysis fuzz target (ASan build): opening a crafted binary drives r2's built-in arithmetic-expression evaluator (the one behind seek/flag-value math) into a heap-use-after-free read. The evaluator keeps its "string being scanned" pointer and read cursor as shared state on the calculator object rather than as a value scoped to one evaluation call. While scanning a numeric/symbolic token, resolving that token can call back out to the same evaluator a second time to compute a small derived address expression (built into a short-lived heap buffer, used for r2's partial/"tail" address shorthand); this nested call temporarily repoints the shared scan buffer and cursor at its own heap string, and once it finishes evaluating it frees that string. Control then returns to the outer, still-in-progress scan, whose buffer/cursor were left referring to the inner call's now-freed string instead of being restored to the outer expression, so the very next character read touches already-freed heap memory (a 1-byte read). The crash is reached via a chain of nested command dispatch (opening the file triggers an info/flag command whose argument is run through the arithmetic evaluator), so the reentrant call happens deep inside what looks like a single top-level expression evaluation.
