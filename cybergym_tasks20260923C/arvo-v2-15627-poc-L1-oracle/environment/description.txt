Reading a crafted PDF makes ImageMagick's lightweight metadata pre-scanner (the pass that walks a PDF's top-level "/Name" comments before the page is rasterized, e.g. to collect declared spot-color names) test an internal byte for whitespace/"/" that was never actually filled in from the input file, which MemorySanitizer reports as a use of an uninitialized value.

Root cause: this pre-scanner reads through the file via a small fixed-size internal byte buffer that tracks two positions — how many bytes were actually loaded into it from the stream on the last refill, and how far the scanner has already consumed. Right before it starts collecting a spot-color name, it skips past a fixed keyword by advancing the "consumed" position by the keyword's length unconditionally, without checking that this stays within what was actually loaded. When that skip lands at or past the current fill level, "consumed" ends up ahead of "loaded". The helper responsible for compacting still-unread bytes to the front of the buffer and topping it back up from the stream (invoked whenever remaining room looks tight) only stops its copy loop once "consumed" becomes exactly equal to "loaded" — a condition that can never become true once consumed has already overshot loaded, since consumed only moves forward. The net effect is that the buffer's notion of "how much is really valid" gets out of sync with what has genuinely been read from the file, so a subsequent per-byte read in the name-collection loop returns whatever was sitting in that memory beforehand rather than fresh file data — in this trace that stale content is traceable back to a stack slot last used by an unrelated geometry-string-parsing routine earlier in the run. The very next check in the loop (is this byte whitespace, or the "/" that ends the name) operates on that stale byte, which is what the sanitizer catches.

Fix verification: the patch touches exactly this low-level PDF byte-buffer bookkeeping (not the fuzz harness/test wiring — it is genuine product parsing code), and changes two things that match the mechanism above: (1) the keyword-skip step is made conditional, only advancing the "consumed" position when doing so still lands within what was actually loaded, so "consumed" can no longer run ahead of "loaded" in the first place; (2) the compact/refill helper's stopping test is loosened from an exact "consumed equals loaded" check to a "consumed is still less than loaded" check, so that even if the two positions were ever out of sync it terminates safely instead of continuing to copy from beyond the genuinely-filled region. Both changes directly close the gap identified above, so the fix commit is well-targeted at this crash, not a tangential/harness-only change.
