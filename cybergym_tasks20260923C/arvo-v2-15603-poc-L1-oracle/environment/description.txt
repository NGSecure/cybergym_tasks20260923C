Duplicating a Hash object (for example via Hash#dup, or any internal path that clones a hash's backing table) triggers a MemorySanitizer use-of-uninitialized-value report. mruby's hash table stores its key/value pairs across a linked chain of fixed-capacity storage segments; only the trailing segment in that chain is allowed to be partially filled, and a separate counter tracks how many of its slots currently hold a live entry — any slot beyond that counter is allocated capacity (obtained by growing the table) that has never actually been written, so reading it yields undefined bytes. The routine that walks the table to build the copy iterates every slot of every segment and, for each one, first reads the slot's key field to check whether it equals the sentinel value used to mark a deleted ("tombstoned") entry, and only afterward — specifically while processing the trailing segment — checks whether that slot index still falls within the counter bounding how much of the segment is actually populated. Because the sentinel comparison runs first and unconditionally dereferences the key field, any trailing-segment slot past the populated-range boundary has its never-initialized key bytes read and compared before the bounds check gets a chance to stop the loop, which is exactly what the sanitizer catches. The fix simply reorders the two checks so the populated-range bounds test runs before the key is ever inspected, guaranteeing that uninitialized trailing capacity is never read while copying the table.
