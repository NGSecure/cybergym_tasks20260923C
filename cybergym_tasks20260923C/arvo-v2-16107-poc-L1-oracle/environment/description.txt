This crash happens while OpenSSL's error-reporting subsystem assembles a human-readable description of a problem encountered while a configuration file is being parsed (the fuzz target feeds arbitrary bytes as a config file, and a malformed directive inside it triggers an error path that wants to report several pieces of context strung together into one message). To build that message, the code keeps a heap-allocated accumulator buffer plus an integer that is meant to track exactly how many bytes are currently allocated for it, and it appends each context fragment onto the buffer in a loop, growing the buffer via reallocation whenever the next fragment would no longer fit. The bug is a mismatch between what that tracked capacity variable claims and what is actually allocated: the growth check treats the new content as still fitting when its length lands exactly on the current tracked capacity (an off-by-one in the comparison — using "still fits when equal" rather than "must be strictly smaller"), so on that exact-boundary case the buffer is never grown, yet the value subsequently handed to the bounded append routine as the destination's available size is computed one byte larger than the buffer that was really allocated. The append routine trusts that inflated capacity value and, because it always writes a terminating null byte after copying, ends up writing that terminator one byte past the true end of the heap allocation — a small, deterministic single-byte out-of-bounds write rather than an unbounded or attacker-sized overflow. It is triggerable by any malformed input that causes the accumulated context text to land exactly at that capacity boundary, and a very similar accounting slip (using a fixed maximum-size constant instead of the actual buffer size that was allocated) exists in a neighboring formatted-error-message code path in the same subsystem, addressed by the same fix.
