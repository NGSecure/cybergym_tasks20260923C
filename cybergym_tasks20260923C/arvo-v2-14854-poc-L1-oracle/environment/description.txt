A crafted IPv6 datagram with a Hop-by-Hop Options header can trigger a stack-buffer overflow while the receive path rewrites an in-transit multicast-forwarding (MPL) option in place. When the option-removal logic decides an MPL option cannot simply be truncated from the header (because other options follow it), it instead overwrites the option's bytes with a generic padding option sized to exactly match the MPL option's declared length, so the header's overall byte layout stays consistent. That declared length is read straight from a single, attacker-controlled length byte in the option header as parsed off the wire, and it is passed on unvalidated — nothing checks it against the small, fixed range of lengths a genuine MPL option can actually have. The padding-option constructor then uses that untrusted value to size a fill operation into its own small fixed-capacity internal buffer, which is itself a field of a stack-allocated object. A declared option length larger than the constructor's internal buffer can hold causes the fill to write past the end of that buffer and past the end of the enclosing stack object, corrupting adjacent stack memory; AddressSanitizer's frame redzone is what actually catches the resulting out-of-bounds write. In short, the root cause is a missing upper-bound check on a wire-supplied option-length field before it is reused to size a fixed-capacity stack buffer write, letting a single crafted option length turn a routine "replace this option with padding" step into a stack buffer overflow.
