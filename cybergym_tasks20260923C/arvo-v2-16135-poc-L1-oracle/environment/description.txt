This crash occurs while FFmpeg's raw/professional CFHD (Cineform-style) video decoder reconstructs a fully decoded frame for a wavelet-compressed Bayer-pattern raw sensor input, where the coded width, height, and Bayer pixel format are all read directly from attacker-controlled bitstream header fields. After combining the low-pass and high-pass wavelet subbands for a plane, the decoder walks the destination picture buffer row by row; on each row it writes a pair of reconstructed 16-bit sample values, one at the current output position and a second at a small fixed additional offset from it so that alternating rows line up correctly with the sensor's Bayer mosaic, and then advances the output pointer to the next row by a per-row stride derived from the destination frame's own linesize. For this Bayer output path the per-row stride is taken directly from the frame's linesize rather than being halved the way it is for ordinary packed 16-bit formats, and the variable holding and accumulating that stride across every row of the frame was declared as an ordinary 32-bit integer rather than a pointer-sized type. For sufficiently large coded dimensions this narrower accumulation lets the effective destination address computed for the later rows of the reconstruction drift slightly from the true, correctly pointer-sized offset into the destination buffer, and that drift shows up on the very last row processed: the second, offset write of the paired sample lands two bytes beyond the end of the plane's heap-allocated pixel buffer, which is sized exactly to the coded frame with no extra padding, producing the observed heap-buffer-overflow write. The fix widens the stride-holding variable to a pointer-sized signed integer type so the same per-row advancement is computed and accumulated without that narrowing, keeping every row's destination write inside the allocated buffer.
