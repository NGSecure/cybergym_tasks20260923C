OpenThread's NCP UART command-processing fuzz target (ASan build): a stack-buffer-overflow read occurs while a Thread network node is building an outbound Address-Notification message to answer a peer's Address-Query CoAP request. Root cause: when the incoming query's Target TLV is parsed off the wire into a small, fixed-size, stack-local structure, the code accepts and keeps the TLV's self-reported length byte exactly as the untrusted peer sent it, instead of resetting it to the structure's true, fixed field width. That same stack-local TLV object is then reused unmodified as an input when the reply message is assembled: the copy routine that serializes each TLV into the outgoing message derives how many bytes to copy from the TLV's own embedded length field rather than from the object's actual allocated size, so a peer that sends a query whose Target TLV claims a length far larger than the structure can really hold causes the reply-building code to read well past the end of that local stack object and into neighboring stack-frame data, which AddressSanitizer catches as an out-of-bounds stack read.
