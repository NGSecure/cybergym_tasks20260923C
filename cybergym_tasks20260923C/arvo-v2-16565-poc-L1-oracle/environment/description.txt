During EXIF metadata parsing of a loaded JPEG image, a routine that derives a human-readable summary value for one metadata entry consults a separate, previously-parsed entry to detect a specific camera vendor and model, doing so by comparing that entry's raw byte content against several fixed-length ASCII identification strings. Before running each comparison, the code confirms only that the referenced entry exists and has a non-null data pointer; it never confirms that the entry's actual stored byte length is at least as long as the identification string it is about to be compared against. When the corresponding tag in the input carries a data payload whose real, allocated length is degenerate — shorter than the string being matched, even by a single byte — the fixed-length comparison still runs at its full width, so it reads one or more bytes past the end of the small heap buffer that was sized to exactly match the entry's short, attacker-controlled length. The overflow is a read, not a write, and it lands on the source vendor/model identification buffer rather than on any output or writable structure; it fires purely as a side effect of formatting one entry's textual value for later attachment to the image, entirely within EXIF header/metadata parsing and well before any pixel data is decoded. Consequently, an otherwise well-formed JPEG whose EXIF block contains a single ASCII tag deliberately truncated to just under one of these fixed comparison lengths is enough to trigger the out-of-bounds read on its own, with no need to touch image content, compression parameters, or any other tag.
