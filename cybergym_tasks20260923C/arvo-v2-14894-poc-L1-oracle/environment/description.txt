GDAL's gdal_translate fuzz target (ASan build): translating a crafted uncompressed GeoTIFF into a new GeoTIFF triggers a heap-buffer-overflow WRITE while a raster block buffer is being filled. Root cause: the input TIFF declares its whole image as a single very large uncompressed strip, so GDAL's embedded libtiff internally re-chops that one strip into many small synthetic sub-strips sized to match the small, fixed-size raster block buffers GDAL allocates for block I/O. The bookkeeping flag that marks a directory's strip offset/byte-count arrays as "already re-chopped" is not correctly (re)established across this rewrite, so a later lookup of a given sub-strip's byte count falls back to the stale, pre-chop value describing the original oversized strip instead of the small chopped chunk size. That inflated byte count then drives the size used to zero-fill the tail of the small, fixed-size block buffer that was allocated for actual block I/O, so the fill writes far past the end of that heap buffer.
