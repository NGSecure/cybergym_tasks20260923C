A crafted X.509 certificate can drive the TLS library's certificate parser to read one byte past the end of a heap-allocated buffer while it is decoding a nested ASN.1 field inside the BasicConstraints extension, an AddressSanitizer-detected heap-buffer-overflow read.

Root cause: BasicConstraints is a small ASN.1 SEQUENCE holding a mandatory boolean flag followed by an OPTIONAL trailing integer. After the parser decodes the mandatory boolean, it must decide whether the optional integer is present, and if so, hand the bytes that follow off to the shared low-level routine that reads an ASN.1 identifier-and-length header, so it can pull out that header before touching the integer's actual value. The bug is in how the parser computes "how many bytes are left to hand off": rather than measuring the remaining space against the true end of the BasicConstraints SEQUENCE's own encoded content, the calculation is anchored to the end of the extension's whole outer buffer, using position bookkeeping that was really meant for tracking progress through the boolean field, not for bounding what comes after it. Because SEQUENCE content does not have to fill its containing buffer exactly, a certificate can be constructed where the true SEQUENCE content ends earlier than the outer buffer, so this miscalculated distance overstates how many bytes are genuinely still available at that position. That inflated count is then passed straight into the shared header-decoding routine as its buffer-length argument. The decoder has no way to know the count it was handed is wrong, so it trusts its caller and, while advancing past the identifier octet to read the accompanying length octet, steps one byte beyond the true end of the underlying heap allocation, believing it is still safely inside the input.
