This crash surfaces in the multi-threaded portion of the H.264 decoder's picture reconstruction and in-loop deblocking stage, specifically inside the worker thread responsible for computing boundary-strength values for the non-MBAFF (progressive, non-field-adaptive) coding path once a slice's macroblocks have been parsed and handed off for parallel reconstruction. Deciding a boundary's filter strength requires knowing which reference picture a neighboring macroblock's motion vector points into, so the routine takes a small, per-macroblock reference-frame index (decoded earlier from the bitstream's motion-vector-prediction data) and uses it directly as a subscript into a small, fixed-size lookup table that maps reference-index values to picture-order-count pointers, with no check that the index actually falls within that table's bounds. The sanitizer reports an eight-byte read through a pointer that lands far outside any valid heap allocation rather than merely a few bytes past a buffer's edge, which is the signature of dereferencing a table entry at a wildly out-of-range subscript rather than a merely-oversized one: a corrupted or unvalidated reference index, rather than the bitstream's ordinary small range of legal values, walks the lookup straight into unrelated heap memory instead of failing gracefully or clamping to a valid table entry. Because the out-of-range index is used to index the table once and the result dereferenced directly, the resulting read address is wild rather than adjacent to the table, and the crash only manifests in the background reconstruction/deblocking worker thread, once per-macroblock motion data has already been decoded and handed off, rather than during header or slice-data bitstream parsing itself.
