In ImageMagick (MSan), rendering an MVG path's bezier/arc-to-bezier primitive can dereference a stale pointer into the shared primitive-point array. The routine that expands a bezier segment first caches a pointer into the current primitive-info buffer, then works out how many interpolated control points the curve needs (based on the spread between its input coordinates) and asks a helper to make sure the buffer has room for that many extra entries; when the buffer must grow, the helper reallocates it, which can move the whole allocation to a new address and invalidate any pointer taken before the call. The vulnerable code goes on to read the curve's endpoint and control-point coordinates through the pointer captured before that possible reallocation, so once the buffer actually moves, those reads fall outside the live allocation - surfacing as an unknown-address read/segfault deep in the bezier-tracing routine, reached only through the arc-to-bezier and generic path-tracing dispatchers above it.

The fix re-derives that pointer from the (possibly now-relocated) buffer right after the room-check call succeeds and before any further coordinate reads, so all subsequent accesses use the up-to-date buffer location instead of the one captured before the buffer could move; a second, purely cosmetic change reorders two adjacent, order-independent statements earlier in the same function and does not by itself affect correctness. Both edits are confined to the bezier-tracing routine in the core drawing-primitive source file - the same file and function identified as the crash site - and touch product code (MVG path rendering), not the fuzz harness, so the fix plausibly explains the observed crash: the crash's dedup token spans exactly the tracing call chain (bezier tracer <- arc-to-bezier tracer <- generic path tracer) whose innermost frame is where the stale-pointer read now gets refreshed.
