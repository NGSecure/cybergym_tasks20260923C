MemorySanitizer reports a use-of-uninitialized-value while the same c-ares fuzz target feeds a raw DNS response through the library's low-level answer-record parsing helper, this time reached through the sibling IPv6 (AAAA) address-reply parser rather than the IPv4 one. That IPv6 parser shares the exact same caller-owned-TTL-array-plus-capacity contract, and the exact same defect, as its IPv4 twin: it copies one TTL/address entry per matching address record into the caller's fixed-size array without ever checking the running write index against the capacity the caller supplied, so a response containing more AAAA records for the queried name than the array can hold drives writes past the end of that stack-allocated array. MemorySanitizer's own report is explicit that it could not establish a clean origin for the flagged value -- an acknowledged limitation of its origin-tracking machinery -- which is consistent with the true fault being this earlier out-of-bounds write silently corrupting unrelated stack state during AAAA-record processing, rather than a genuinely-never-initialized local variable at whatever spot the tool happens to attribute the read to. The reported crash site should therefore be read as a downstream symptom of that corruption, not as the location of the actual defect, and the real bug is best understood as the same missing-bounds-check pattern that produces a directly-observable overflow in the IPv4 counterpart.
