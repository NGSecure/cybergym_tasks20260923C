The crash sits in the code path that inspects a small metadata block carried inside a JPEG marker segment to decide whether it looks like a URL-prefixed text payload worth extracting, followed by a null terminator, before the real trailing content. Once a coarse "does it start with a recognizable URI scheme" check passes, the routine assumes it is always safe to scan forward through a fixed, hardcoded number of bytes looking for that terminator, and it never limits this scan to the buffer's actual, reported size before doing so or before reading the byte that decides whether a terminator was ever found. The declared length of the marker's payload can be much smaller than that hardcoded scan width while still satisfying the shallow prefix test, so a malformed or truncated marker whose real data region is shorter than the assumed width lets the terminator-search step, and the read that follows it, walk one byte past the end of the small heap allocation backing that marker's data — reported by the sanitizer as a one-byte out-of-bounds read. The underlying defect is a missing floor on the scan bound: nothing derives the loop's true upper limit from the smaller of the fixed assumed maximum and the payload's real length, so a short enough marker lets the scan and its trailing check run off the end of the buffer instead of safely concluding that no terminator was present within the data actually supplied.
