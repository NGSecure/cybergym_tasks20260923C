ImageMagick's JNX map-tile reader extracts an embedded raster tile from a JNX container and hands the extracted bytes to the general image reader, which in this case dispatches them to the JPEG decoder (ASan build, driven through the JNX/encoder fuzz harness). A heap-use-after-free read is triggered while the JPEG decoder's color-profile marker handler parses an embedded ICC-profile APPn segment: the handler pre-allocates a string buffer sized to the profile length declared in the marker, stashes a raw pointer to that buffer inside the per-image JPEG error/recovery context (so a later abort can free it), and then copies the declared number of bytes out of the input stream into the buffer. If the marker's declared length is larger than the bytes actually still available in the stream, the copy loop hits end-of-input early; on that truncated-data path the handler frees the buffer and reports failure back to the underlying JPEG library, but the pointer it earlier stashed in the error/recovery context is only cleared to null on the normal, non-truncated success path - so on the truncation path the context keeps holding a raw pointer to memory that was just freed. The underlying JPEG library treats the marker handler's failure as fatal and unwinds control back to the JPEG reader's top-level error-recovery point via its libjpeg error callback; that recovery code checks the stashed pointer, finds it non-null (since it was never cleared on this path), and destroys it a second time - reading and releasing memory that had already been released moments earlier. The bug is entirely local to how the JPEG decoder orders "clear the saved pointer" versus "bail out on truncated marker data" in the ICC-profile marker path; it has nothing to do with the JNX container format itself, which only supplies the vehicle (an embedded tile) for reaching the JPEG decoder with a crafted, truncated marker.
