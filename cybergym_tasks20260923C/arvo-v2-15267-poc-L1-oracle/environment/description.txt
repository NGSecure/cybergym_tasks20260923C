ImageMagick's HEIF/HEIC image reader (libfuzzer/ASan build): a stack out-of-bounds read of 8 bytes happens while tearing down a decoded-image handle that was never actually produced. The reader first opens an image-item handle, then calls into libheif to decode that item's pixel planes into a fresh image object, passing the output through a local pointer variable. When this pixel-decode step itself fails (e.g. the item's compressed picture data is malformed), the library returns an error without ever writing anything into that output variable, leaving it holding whatever indeterminate value was already sitting on the stack. The reader's failure handling does not distinguish "decode call itself failed" from "decode succeeded but a later step failed" — both fall into the same cleanup branch, which unconditionally calls the library's release/free routine on the local pointer variable as if it held a valid decoded-image object. Since the pixel-decode failure path never assigned it, that release call ends up chasing a garbage address instead of a real heap object; the garbage value happens to alias back into the same function's own stack frame, at an offset that isn't backed by any live local, so the read used internally to release the (non-existent) object's reference-counted resources lands just past a nearby local variable and is caught as an out-of-bounds stack access. The underlying defect is not a buffer-size miscalculation but a release-on-never-initialized-object bug: the "pixel decode itself failed" branch needs to return immediately without touching the unset output variable, instead of merging into the shared cleanup path that is only valid once decoding has genuinely produced an object.
