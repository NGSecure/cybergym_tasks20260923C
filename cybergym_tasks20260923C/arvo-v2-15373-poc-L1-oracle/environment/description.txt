This is a heap-buffer-overflow read in c-ares's DNS-reply-to-hostent conversion path for AAAA (IPv6) answers: when parsing a raw DNS response into a hostent structure, the address-list builder walks every node of an internal linked list of parsed address records and, for each entry, copies a fixed-size 16-byte IPv6 address field out of that record's stored socket-address buffer, regardless of the actual address family the record was parsed as. The lower-level DNS-response walker that builds this linked list allocates each entry's socket-address buffer sized to match that entry's own record type - a shorter buffer for an IPv4 (A) answer than for an IPv6 (AAAA) answer. If the response for the queried name mixes A and AAAA answer records together, the resulting list contains at least one node whose buffer was sized only for the shorter IPv4 structure. Because the AAAA-side conversion routine never checks each node's family before performing its fixed 16-byte IPv6-address copy, it ends up reading the IPv6 address field - which sits at a deeper byte offset than the IPv4 field occupies - straight out of that undersized buffer, running past the end of the heap allocation and triggering the overflow read.
