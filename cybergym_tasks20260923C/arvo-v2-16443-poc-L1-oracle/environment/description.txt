This is a GeoTIFF-reading crash reachable through the library's high-level "read as RGBA raster" path, which walks a strip-oriented image one row-span at a time and, for each span, works out how many bytes of that span still remain to be pulled in before it hands that count off to the lower-level strip-fetch/decode machinery. The remaining-bytes figure is derived purely from 32-bit unsigned quantities — the row's position modulo the configured rows-per-strip, plus the number of rows still to process in the current span, multiplied by the per-row byte width implied by the image's declared geometry. A pathological but well-formed input can drive the row width and/or the rows-per-strip/row-count terms in this computation large enough that the multiplication wraps around the 32-bit boundary rather than raising an error, producing a "bytes remaining" value that bears no true relationship to the real amount of data available or to the size of the buffer that was actually (and separately) allocated to hold it. That corrupted count is then passed straight down as the length to decode/copy for the current strip; when later reinterpreted as a signed size it comes out negative, and the raw byte-copy step that ultimately executes on it aborts immediately because the requested copy length is nonsensical (effectively an enormous or negative size) relative to any real buffer, rather than the process silently reading or writing out of bounds. In short, an attacker-controlled image whose row/strip dimensions are large enough forces an unchecked size computation feeding the strip-decoding step to overflow, so a wrong, wildly-out-of-range length reaches a raw memory copy instead of the true remaining byte count for that strip.
