This is a heap-buffer-overflow read of four bytes, one word past the end of the codec's working input buffer, that surfaces while a fuzzed H.264 elementary stream is being CAVLC-decoded inside an intra slice's macroblock residual parsing. The overflow is not caused where it is finally observed; it is the delayed symptom of an earlier accounting bug in the routine that reconstructs zero-run positions for a transform block's non-zero coefficients. That routine tracks two related quantities, a remaining zero-run count and a running scan-position index, both of which should legitimately fall to a negative value on malformed input as a signal that the decoded run/level syntax elements are inconsistent with the block's stated coefficient count; the routine did carry a check meant to catch exactly that, but the tracked quantities were declared as unsigned counters, so a genuinely negative result instead wraps around into a very large positive value and the "less than zero" guard can never fire. With the corruption undetected, parsing simply continues as if nothing were wrong, and the code's notion of how many bits of the compressed bitstream have actually been consumed silently drifts out of sync with the real, wrapped-around count. That drift is cumulative rather than immediately fatal: subsequent syntax elements are parsed at slightly wrong bit offsets without producing a visible fault at first, and it is only later, when a following coefficient token for a nearby 4x4 block is decoded by directly indexing into the shared bitstream storage at the now-corrupted offset, that the read finally lands past the boundary of the heap allocation backing that storage and the sanitizer reports the crash. In short, a signedness mistake in a bounds check meant to reject inconsistent run-length/coefficient-count combinations lets attacker-influenced bitstream fields desynchronize the decoder's internal bit-position tracking, and that desynchronization is what a later, otherwise-unrelated read step ultimately trips over.
