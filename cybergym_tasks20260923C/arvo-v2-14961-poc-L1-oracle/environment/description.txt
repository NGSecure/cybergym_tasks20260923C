The karchive fuzz target opens a KTar archive whose underlying stream is gzip-compressed via KArchive's generic compression-device wrapper, which sits between Qt's QIODevice and the actual gzip/zlib decompression backend implemented by the archive's compression filter.

When the archive-opening logic needs to move the read position of that compressed stream forward by a large, input-controlled number of bytes (implemented as a series of throwaway reads that discard everything between the current offset and the target one), it allocates a single fixed-size scratch byte buffer capped at a small constant number of kilobytes, then asks the underlying device to fill that scratch buffer with the entire remaining distance still to be skipped in one call, rather than with the buffer's own, smaller capacity. Whenever the requested jump is large enough that the distance still to be discarded exceeds that cap, this issues one read/decompress request for more bytes than the destination buffer can actually hold.

The decompression backend honors that oversized request literally. For inputs where the gzip archive filter's internal logic takes its no-decompression / raw pass-through branch (a short-circuit path distinct from the branch that actually drives zlib's inflate machinery), the bytes are delivered into the destination via one bulk memory copy sized to the caller's requested byte count, with no check against the destination buffer's real allocation size. The result is a small (a couple of bytes) but real heap write past the end of a roughly 24KB scratch allocation, observed under AddressSanitizer as a heap-buffer-overflow WRITE landing immediately at the first byte past the buffer's allocated region.

Trigger conditions: a gzip-wrapped tar archive whose compressed payload is large enough, and shaped so that the archive filter's raw pass-through branch handles it instead of genuine zlib inflate decompression, that a single forward-positioning request made while KTar opens the archive needs to discard, in one call, more bytes than the wrapper's internal scratch buffer was sized to hold. The overflow write itself happens inside the archive filter's own raw-copy routine, one layer above the zlib library proper -- zlib itself is not at fault here.
